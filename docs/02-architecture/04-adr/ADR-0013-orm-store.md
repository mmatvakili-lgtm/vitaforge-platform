# ADR-0013 — لایه ذخیره‌سازی ORM به‌جای Store حافظه‌ای

| فیلد | مقدار |
|---|---|
| Status | Accepted (پیاده‌سازی: Not Started) |
| Date | 2026-11-09 |
| Owner | Architect |
| Related | DEC-153، ADR-0007 |

## مسئله

سرویس‌های دامنه (~۸۰۰ خط در `app_services/`) مستقیماً به `InMemoryStore` وابسته‌اند و دیکشنری‌ها را درجا تغییر می‌دهند (مثلاً `m["status"] = ...`). این رفتار با ORM پایدار نمی‌شود مگر `save()` صریح باشد.

## گزینه‌ها

- A) لایه شبیه dict روی ORM: تغییر درجا ذخیره نمی‌شود؛ خطای پنهان داده. **رد.**
- B) بازنویسی سرویس‌ها روی ORM: ریسک بالا برای ۴۰۵ تست.
- C) **پورت Repository صریح** (متدهای `get/save/list_*` به‌ازای هر تجمیع) با دو پیاده‌سازی: `InMemory` و `Django ORM`. سرویس‌ها فقط از پورت استفاده می‌کنند و یک مجموعه تست انطباق (conformance) روی هر دو اجرا می‌شود.

## تصمیم: C، مرحله‌ای

1. فهرست‌برداری از همه نقاط تغییر درجا (برای هر collection در Store).
2. تعریف پورت و پیاده‌سازی InMemory؛ ۴۰۵ تست فعلی باید بی‌تغییر سبز بمانند.
3. مجموعه conformance روی پورت (CRUD، یکتایی، جداسازی کاربر، رفتار تراکنش/rollback).
4. پیاده‌سازی ORM + `makemigrations` واقعی (migrationها هرگز دستی نوشته نمی‌شوند) و اجرای conformance روی PostgreSQL.
5. تراکنش: هر عملیات API داخل `transaction.atomic()`؛ شکست = rollback کامل، از جمله `audit`.
6. جداسازی کاربر در سطح Query: هر متد Repository داده‌ی کاربر `user_id` را اجباری می‌گیرد؛ دسترسی بدون آن وجود ندارد.

## پیامد

مراحل ۳–۴ و تست‌های Postgres نیاز به محیط دارای Django/psycopg دارند (OPEN-013).
